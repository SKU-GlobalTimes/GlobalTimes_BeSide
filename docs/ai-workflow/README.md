# AI 작업 운영 규칙

## 목적

AI를 단순 코드 생성 도구가 아니라 조사, 계획, 구현, 검토를 분리해 지원하는 개발 도구로 사용한다.
모든 변경은 사람이 승인한 범위 안에서 수행하며, 나중에 근거와 결과를 재현할 수 있어야 한다.

## 기본 흐름

```text
조사 → 계획 제안 → 사용자 승인 → GitHub Issue → 작업 브랜치 → 구현 → 검증 및 리뷰 → PR → 사용자 확인 후 Merge
```

Reviewer 세션을 별도로 운영하는 경우에는 GitHub PR comment를 중심으로 리뷰 결과와 반영 내역을 기록한다.
자세한 흐름은 [AI Reviewer PR Comment Workflow](./reviewer-comment-workflow.md)를 따른다.

## 역할 분리

| 역할 | 책임 | 코드 수정 권한 |
| --- | --- | --- |
| 조사자 | 기존 구조, 영향 범위, 위험 요소, 대안을 확인 | 없음 |
| 계획자 | 작업 범위, DB 영향, 테스트, 롤백 방법을 제안 | 없음 |
| 구현자 | 승인된 Issue와 계획 범위 안에서 변경 | 승인 후 가능 |
| 검토자 | 범위 이탈, 예외 처리, 누락 테스트, 운영 위험을 검토 | 없음 |

한 작업에서 같은 AI가 역할을 수행할 수는 있지만, 검토 단계에서는 구현 관점과 분리해 확인한다.
별도 Reviewer 세션은 코드 수정, 커밋, push, merge 권한 없이 PR diff 검토와 PR comment 작성만 수행한다.

## 승인 게이트

다음 작업은 사용자 승인 전에는 수행하지 않는다.

- 코드, 설정, DB 스키마 변경
- 브랜치 생성 및 원격 push
- GitHub Issue 또는 PR 생성·수정
- 데이터 삭제, DB 마이그레이션, 배포
- 비밀값, 인증 정보, 외부 서비스 권한 변경

구현 중 승인된 범위를 벗어나거나 DB 영향이 새로 발견되면 작업을 멈추고 계획과 Issue를 갱신한다.

## GitHub 기록 기준

| 기록 | 위치 |
| --- | --- |
| 문제, 목표, 범위, 완료 기준 | GitHub Issue |
| 실제 변경 이력 | 작업 브랜치와 커밋 |
| 계획 대비 변경점, 테스트·성능 결과 | PR 본문 |
| AI Reviewer 검토 결과와 반영 내역 | PR comment |
| 중요한 기술 선택과 대안 | `docs/adr/` |
| 개선 후보와 우선순위 | `docs/backend-improvement/BACKLOG.md` |

PR은 해당 Issue를 `Closes #번호`로 연결한다.

## 로컬 전용 기록

다음 정보는 GitHub에 원문 그대로 기록하지 않는다.

- API 키, 토큰, 비밀번호, 인증 코드
- 사용자 식별 정보와 원본 대화
- 원본 프롬프트 전문과 민감한 모델 응답
- 대용량 서버 로그와 외부 서비스 응답 전문

GitHub에는 필요한 경우 실행 시각, 역할, 모델명, 대상 작업, 성공/실패, 테스트 결과처럼 재현에 필요한 최소 메타데이터만 남긴다.

## 작업 계획 최소 항목

각 구현 작업은 Issue 또는 연결 문서에 아래 내용을 포함한다.

- AS-IS와 해결하려는 문제
- TO-BE와 변경 범위
- 영향 받는 모듈, API, DB
- 위험 요소와 롤백 방법
- 테스트 및 측정 방법
- 완료 기준(Definition of Done)
